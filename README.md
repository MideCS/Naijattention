# Naijattention

Does adding a cross-lingual contrastive objective to translation cross-entropy improve English → Nigerian
Pidgin translation with mT5-small? This repository compares a cross-entropy baseline with
cross-entropy + λ · symmetric InfoNCE. Both models start from the same pretrained weights and get the same
data, budget and decoding settings. They're evaluated on chrF++ and on encoder sentence-retrieval accuracy (R@1).

The full specification is in [`docs/implementation_plan.md`](docs/implementation_plan.md). The top of that
file lists where the implementation deliberately differs from the original plan.

## Data

| Source | Use | Rows (usable) | Licence |
|---|---|---|---|
| MAFAND-MT en-pcm (news) | train / **dev / test** | 4,790 / 1,484 / 1,564 | CC BY-NC 4.0 |
| UD Naija-NSC (spoken) | train / **dev / test** | 7,278 / 990 / 972 | CC BY-SA 4.0 |
| MTurk_Pidgin.csv | train only | 23,382 | unconfirmed |

Files are downloaded on first use into `data/raw/`, pinned to exact commits, and checked against expected
row counts. Training rows whose normalised English **or** Pidgin appears in any dev/test set are removed
(310 rows), as are duplicate pairs, which leaves 35,058 training rows. Validation and test are the published
splits, reported per source.

## Run locally

```bash
uv venv .venv --python 3.12
uv pip install --python .venv/Scripts/python.exe torch --index-url https://download.pytorch.org/whl/cu124
uv pip install --python .venv/Scripts/python.exe -r requirements.txt
.venv/Scripts/python.exe -m pytest -q                               # unit tests, ~20 s
.venv/Scripts/python.exe scripts/run_experiment.py --smoke          # end-to-end smoke test, ~3 min
```

The smoke test uses 64 training rows and 6 updates per model. It exercises every code path, but its numbers
**are not results**. To execute the notebook in smoke mode:
`NAIJA_MODE=smoke jupyter nbconvert --to notebook --execute notebooks/naijattention.ipynb --output-dir outputs/smoke`.

## Run on Colab

1. Open `notebooks/naijattention.ipynb` in Colab (File → Open notebook → GitHub → `MideCS/Naijattention`)
   and choose an **A100** runtime. The first cell clones or updates this repo, installs it, and mounts
   Google Drive. Outputs go to `MyDrive/naijattention/outputs/`.
2. **Pilot first.** With `RUN_MODE = "pilot"` (the default), do Runtime → Run all. This uses the full data
   and the whole pipeline, capped at 300 updates per model (estimated 10–15 minutes). Check the
   training-health table: the MT loss should fall well below about 5, and validation outputs should be
   non-empty real Pidgin.
3. **Full run.** Set `RUN_MODE = "full"` and Run all again.

**If Colab disconnects,** re-run all cells. Each finished training run is detected (same settings, by
config fingerprint) and reused, so only the unfinished model retrains. Partway through a model there is no
resume: an interrupted model restarts from scratch. Changing a training setting with the same output folder
is refused rather than silently mixing runs. Use a new folder, or `overwrite=True`.

CLI equivalent: `python scripts/run_experiment.py --pilot --output-root /content/drive/MyDrive/naijattention/outputs`,
then the same command without `--pilot`.

**GPU memory.** Peak memory measured for the worst-case (length-128) contrastive batch, using BF16 and Adafactor:

| Batch | Peak memory |
|---|---|
| 8 | about 5.2 GB |
| 16 | about 8.4 GB |
| 32 | about 15 GB (extrapolated) |

- **L4 / A100 (BF16):** the default `batch_size=32` should fit.
- **T4 (FP32, no BF16):** set `gradient_checkpointing=True` in the config cell, or use
  `batch_size=16, gradient_accumulation_steps=2`. Accumulation halves the number of in-batch negatives, so
  state that in the write-up if you use it.

Each fp32 checkpoint is about 1.2 GB, so a pilot plus a full run uses about 5 GB of Drive.

Outputs go to `<output root>/pidgin_mt5/` (or `pilot/`):

- `config.json`, `environment.json`, `data_audit.json`
- `splits/`
- `<run>/best/` (model and tokenizer) and `<run>/train_history.json`
- `results/`: `translations.csv`, `metrics.json`, the human-evaluation template and key, `integrity_checks.json`
- `figures/`


## Integrity rules built into the code

- Test data is used only in `evaluate_test`. The contrastive λ and the checkpoint epoch are chosen on validation chrF++.
- Both runs share the same initialisation, batch order, optimizer, schedule, update count and decoding settings.
  The integrity checks verify this.
- chrF++ is computed with SacreBLEU (`word_order=2`) on whole corpora, per source. The paired-bootstrap 95%
  CIs reflect test-sample noise only, not seed variance. Run multiple seeds before claiming an effect.
- Human evaluation is blinded (A/B order shuffled per row), and scores are never generated by the code.
